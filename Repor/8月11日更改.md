# MoreAIPlayer「8月11日更改」实施报告

> 文档性质：交给下一名 Agent 的冻结需求、实现路线和验收合同。  
> 本文已经替用户作出必要选择。除非本机 tModLoader API 与本文写明的接口方向发生无法编译的冲突，否则不要中途向用户提问；先检查本地源码，再选择同语义的当前 API 完成实现。  
> 本轮要求修改代码，但当前撰写报告的 Agent 不修改任何源码。

## 0. 结论与实施顺序

下一名 Agent 按以下顺序工作，每一阶段单独编译、检查差异后再继续：

1. 修复平台战斗时无条件下落，并补齐绳索导航。
2. 做多人模式安全审计与自动化检查；仍不对外开放多人召唤，但必须保证客户端、服务器、进出世界和断线过程不崩溃、不污染真实玩家槽位、不改错世界。
3. 对自动书做第二轮架构审计，先补“看门狗、诊断、恢复策略”，再扩展流程分支；不得继续在当前线性优先级列表上盲目叠功能。
4. 新增默认关闭的“普通幻影伙伴敌对玩家”配置。只作用于调试书的普通伙伴，不作用于猎人、运行中的自动伙伴，也不应把通关后的自动伙伴悄悄纳入，除非其 profile 被用户明确转换为普通调试伙伴身份。

优先级理由：平台误降会影响所有普通伙伴，也会污染后续自动伙伴战斗；多人安全边界决定新配置和伤害路由应放在哪里；自动书的恢复框架应早于更多流程内容；敌对配置最后接入已经稳定的伤害与网络权限层。

## 1. 当前代码审计结论

### 1.1 平台误降的直接原因

相关文件：

- `Companion/AI/CompanionNavigator.cs`
- `Companion/AI/CompanionPathfinder.cs`
- `Companion/AI/CompanionBrain.cs`
- `Companion/AI/CompanionThreatAvoidance.cs`

已确认的现状：

- `CompanionPathfinder` 只有 `Move` 和 `DropThroughPlatform` 两种路径动作，没有绳索动作。
- `CompanionNavigator.FollowPath` 遇到 `DropThroughPlatform` 会按下 `controlDown`，这是合理的显式路径动作。
- 但 `FollowPath` 还有一个额外分支：只要当前 waypoint 比伙伴低超过约 40 像素并站在平台上，即使当前路径步骤不是 `DropThroughPlatform`，也会按下 `controlDown`。
- `DirectSteer` 同样在目标低于约 48 像素、横向距离不大时直接按下 `controlDown`。
- 战斗中的 `PositionForCombat` 仍调用同一个 `Navigate`，因此敌人在平台下方、武器理想位置略低、避让目标较低或路径回退到直线控制时，都可能把普通的“向低处靠近”误解释成“主动穿过脚下平台”。
- 现有代码没有检查平台下方是否真的有安全落点，也没有检查落差、岩浆、敌弹、战斗射线、当前战斗层或是否仍可站在原平台攻击。

因此评论区描述与源码完全吻合。这不是单纯调高一个距离阈值能可靠解决的问题，必须把“想去低处”和“批准穿平台”拆成两个不同决定。

### 1.2 绳索目前不是“表现不好”，而是没有模型

寻路图只把固体块和平台当成支撑面，没有绳索节点、进入绳索、沿绳索上下移动、离开绳索等边。导航器也没有稳定的 `controlUp/controlDown` 攀爬状态。因此不能用几条临时按键判断宣称已经支持绳索。

### 1.3 多人模式当前是“主动禁用 + 局部防泄漏”

当前合成伙伴占用 `Main.player` 的真实槽位，并通过 `VirtualPlayerExecutionContext` 临时替换 `Main.myPlayer` 和鼠标/方块目标，让原版 `Player.ItemCheck` 工作。这个方案在单人模式成立，但不能直接把空闲高位槽当成多人模式中的额外玩家：服务器连接、玩家同步协议和客户端槽位所有权都会与它冲突。

目前已经有不少正确保护：召唤、伤害、ItemCheck detour、投射物 detour、UI 等处会检查 `SinglePlayer`，netMode 改变时释放合成槽位，并有 `Main.myPlayer` 泄漏恢复。但没有统一的运行策略类，也没有数据包层、服务器权威模型或多人自动测试。大量分散判断很容易在新增功能时漏掉。

本轮“代码层级支持多人”定义如下：

- 对外仍显示“暂不支持多人”，多人世界中不能召唤这些合成 Player。
- 模组必须能在多人客户端和专用服务器安全加载、连接、游玩、断线、换世界和卸载。
- 所有单人专用 detour、槽位表、世界修改、伤害模拟和 UI 都必须在多人下可靠失效，不留下上一个单人世界的合成实体或投射物。
- 新增统一权限边界和可测试的网络状态机，为以后真正采用服务器权威的代理实体架构留下接口。
- 不允许为了“看起来支持”而把当前合成 Player 强行同步到服务器。真正的多人伙伴若将来开放，应改用服务器权威的 `ModNPC`/专用代理实体或另一套明确不会占用连接玩家槽位的架构；本轮不做这个大迁移。

### 1.4 自动书目前只完成早期资源闭环

当前 `AutoProgressionPlanner` 的实际终点是：工作台、熔炉、铁砧、基础金属装备和初始房屋。完成房屋后返回 `Idle(RetryLater)`。以下目标虽然出现在枚举或旧报告中，但没有完整执行链：

- 全世界分帧知识扫描和兴趣点缓存。
- 宝箱搜索、合法开箱、跑鞋等机动装备选择。
- 背包满后的存箱；`DepositSurplus` 尚未接入，而采集器在背包满时会返回 `RetryLater`。
- NPC 入住、商人购买、虫网与购买白名单；`Shop` 尚未接入。
- 生命水晶、魔力水晶和生命果的实际寻找、使用及持久计数递增。
- 钓鱼、水体评估、鱼饵准备和宝箱替代路线。
- Boss 策略、召唤条件、场地、失败升级与从困难模式到月亮领主的主线。
- 特殊世界和模组进度提供器。

更重要的是：当前没有真正的卡住看门狗。

- 只有 `AlternativeRequired` 会触发表面左右游走。
- `RetryLater` 会在下一帧原样重试，没有退避、截止时间和替代目标。
- `Blocked*`、`Faulted` 等结果没有统一处理。
- 游走只用横坐标判断 60 tick 是否没动，然后反向；没有记录任务是否取得资源、是否减少距离、是否改变世界、是否重复命中同一不可达目标。
- 没有持久化当前目标、尝试次数、失败原因、恢复层级和诊断摘要。

所以“某件事卡住后怎么办”的准确答案是：目前大多数情况下没有足够可靠的处理，部分任务会左右换向，另一些会无限重试。这一轮必须优先修复。

## 2. 任务一：平台与绳索智能化

### 2.1 引入导航意图，不再让坐标差直接决定穿平台

新增一个轻量的导航请求结构，例如：

```text
NavigationRequest
  GoalWorld
  Intent: Follow / Combat / Escape / Build / Mine / Waypoint / Explore
  AllowPlatformDrop
  AllowLedgeFall
  PreferKeepElevation
  MaximumSafeDropTiles
```

命名可按项目风格调整，但语义必须完整。保留旧 `Navigate(Player, Vector2)` 作为安全默认重载时，其默认值必须是“不主动穿平台”。所有确实需要向下的调用点明确传递许可。

规则冻结如下：

- `Follow`：只有主人明显位于下层且存在已验证落点时允许穿平台。
- `Combat`：默认保持当前作战层。敌人在下面不等于必须跳下去；远程、魔法、召唤武器能在原层攻击时绝不降层。
- `Escape`：由危险评估批准，可快速下落，但仍禁止落入岩浆、微光、致命落差或预测弹幕区。
- `Build`、`Mine`：只有目标任务明确要求下层方块，且落点/路线可恢复时允许。
- `Waypoint`：用户明确点在下层时可允许，但仍走安全落点检查。
- `Explore`：把穿平台作为有成本的路径边，不作为直线回退的默认动作。

删除或严格门控 `FollowPath` 与 `DirectSteer` 中“只因目标更低就按下”的通用分支。只有当前 `PathStep` 明确是批准后的 `DropThroughPlatform`，或导航请求通过安全检查，才可设置 `controlDown`。

### 2.2 平台下落许可检查

新增集中函数，禁止在不同脑中复制半套判断。建议接口：

```text
TryApprovePlatformDrop(player, request, out landingTile, out reason)
```

至少检查：

1. 脚下确实是 `TileID.Sets.Platforms`/合法的模组平台，而不是斜坡、门或半砖误判。
2. 下方有限距离内存在可以容纳玩家身体的落点；普通移动建议上限 12–16 格，装备有防摔能力时也不能无限放宽。
3. 落点不是岩浆、微光、持续伤害方块，不位于立即可预测的敌对弹幕碰撞区。
4. 路径穿过的竖直通道可容纳身体。
5. 下落后仍在 hold/combat leash 内，并有返回当前层的已知路线；否则战斗中拒绝降层。
6. 当前武器能从平台上命中目标时，战斗请求拒绝降层。
7. 最近刚穿过一层平台时进入短冷却，防止一口气连续掉穿多层。建议 12–20 tick 冷却，并在真正越过平台后才开始计时。
8. 记录一次“下落承诺”：按键只保持到身体越过目标平台，随后立即释放，不允许残留 `controlDown` 继续穿下一层。

战斗额外保存 `CombatSupportY` 或当前平台段。目标仍在同一战斗、伙伴未被击落且当前层可攻击时，作战定位应围绕这个高度生成。近战确实必须接近下层敌人时，才申请一次有落点的降层。

### 2.3 绳索寻路

先查本机 tModLoader/Terraria 当前版本对原版绳索、藤蔓、链条及模组绳索的注册方式。若没有统一的 `TileLoader` 绳索集合：

- 原版使用明确的原版集合/ID。
- 提供 `CompanionRopeRegistry`，允许兼容层注册模组绳索 tile type。
- 不要把所有非实心竖直家具猜成绳索。

给路径动作增加：

- `EnterRope`
- `ClimbRopeUp`
- `ClimbRopeDown`
- `ExitRope`

寻路边规则：

- 身体与绳索列相交时可以产生上下相邻节点。
- 地面节点可通过短横移/跳跃进入可够到的绳索。
- 绳索节点可在相邻可站立平台或地面退出。
- 上下移动成本低于反复跳墙，但高于平地行走，避免远处有绳索就绕巨大远路。
- 绳索中断、被玩家拆除或变成不可用 tile 时立即重新寻路。

执行规则：

- 进入绳索前先水平对齐，避免一边远离绳索一边按上。
- 攀爬时导航器独占上下移动，普通战斗定位不能同帧覆盖。
- 可在绳索上使用武器，但不得因为目标在下方就自动松开绳索；只有安全落点请求批准才离开。
- 遭受击退脱离绳索后，重新评估最近安全落点或重新抓回，不重复按上卡在空中。

### 2.4 平台/绳索验收场景

必须实机测试，不得只编译：

- 三层平台，最下面没有地面：敌人在下一层，远程伙伴保持当前层攻击。
- 三层平台，下面有安全地面：近战伙伴在确有必要时只穿一层，不连续掉到底。
- 平台下为岩浆、微光、尖刺或高密度弹幕：拒绝下落并换位/换武器。
- 锤击平台、模组平台注册平台、门旁平台、平台楼梯。
- 主人在下层的跟随、用户 waypoint 在下层、逃避致命弹幕三种允许下落场景。
- 一根连续绳、断绳、绳索接平台、绳索跨洞、模组注册绳索。
- 绳索上遭击退、攻击、切换目标、目标死亡和路径中途被拆除。

## 3. 任务二：多人模式代码级安全与自动化检查

### 3.1 统一运行权限

新增集中策略，例如 `CompanionRuntimePolicy`，至少暴露：

```text
CanRunSyntheticPlayers       // 仅单人
CanMutateWorld               // 单人，或未来服务器权威路径
CanRunLocalUI                // 非专服且仅本地玩家
CanRunNetworkCleanup         // 客户端与服务器均可，但只能清本模组状态
IsAuthoritativeDamageSide    // 单人；未来多人为服务器
```

把关键入口改为调用策略，不再到处重新解释 `netMode`。原有局部保护可以保留为第二层防线。

重点入口：

- `CompanionEntitySystem.Summon/PreUpdatePlayers/ReleaseAll`
- `VirtualPlayerExecutionContext.Enter/ForceRestoreIfLeaked`
- Player/Projectile ItemCheck detour
- `RunCompanionDamagePass`
- `CompanionBuildingSystem`
- 自动伙伴所有 WorldGen、拾取、合成和完成标志写入
- UI、模式轮、背包、快捷键
- Hunter 系统与玩家倍率书

### 3.2 多人安全合同

- 多人客户端或服务器收到书本使用时，只在发起客户端显示“不支持多人”，不在每台客户端重复刷消息。
- 不创建、替换或激活任何 `Main.player` 合成槽位。
- 从单人世界切到多人、主机模式或服务器时，先恢复真实 `Main.player[slot]`，再清空注册表；不得杀死该槽位当前属于真实玩家的投射物。
- 所有 `Main.myPlayer` 替换必须处于单人策略内并由 `try/finally` 恢复；专服路径不得读取 `Main.LocalPlayer`、鼠标、屏幕尺寸或 UI 状态。
- 多人客户端不得本地执行 `WorldGen.PlaceTile/PlaceWall/OpenDoor/CloseDoor` 等权威世界修改。
- 客户端配置不得决定服务器伤害、阵营或世界写入。影响玩法的新配置使用 `ServerSide` 配置或显式服务器状态；纯 UI 设置继续留在 ClientSide。
- 不添加没有消费者的数据包。若为未来扩展建立 packet enum，未知包、版本不符、长度错误必须安全丢弃并记录一次限频日志，不能信任客户端传来的 profile、物品或世界坐标。
- 客户端永远不能要求服务器直接“给物品、完成任务、设置 downed flag、扣某玩家血”；客户端只提交意图，服务器验证所有权、距离、身份和条件。

### 3.3 自动化审计与测试

下一名 Agent 应增加仓库内可重复运行的检查脚本或测试项目，但不要把 Codex 临时文件放进发布包。检查至少覆盖：

1. 扫描所有 `Main.LocalPlayer`、`Main.myPlayer =`、鼠标、UI、`WorldGen` 写操作、`NetMessage` 和 `Main.player[slot] =`，要求它们位于批准的策略或明确的服务器/客户端分支。
2. 检查所有书本与 UI 在 `Main.dedServ` 下不会实例化客户端界面。
3. 检查所有合成槽位注册表在 `OnWorldUnload`、`Unload`、netMode 改变和异常恢复后为空。
4. 检查伤害只能在权威侧结算一次；客户端不得先扣血再由服务器重复扣血。
5. 检查投射物 owner 修正不会把真实联网玩家的投射物重写到合成槽。

人工/自动启动矩阵：

- 单人召唤伙伴后返回菜单，再加入多人服务器。
- 先加入多人再退出并进入单人。
- 专用服务器无玩家启动、首个玩家加入、第二个玩家加入、玩家断线、服务器换图/关闭。
- 客户端手持并点击所有书；只收到本地拒绝，不生成实体和世界修改。
- 模拟注册表残留后进入多人，确认只清模组记录，不动真实玩家和投射物。
- 至少持续运行 10 分钟，监控 `Main.myPlayer`、活跃玩家计数、槽位身份、投射物 owner 和异常日志。

“编译通过”不能视为多人验收。若环境无法启动双客户端，报告必须明确写“静态和专服冷启动通过，双客户端尚未验证”，不可写成多人已支持。

## 4. 任务三：自动书第二轮修复与翻新

### 4.1 先建立真正的任务运行时

不要再让脑每帧临时选择一个 `AutoPlan` 后丢掉全部上下文。新增并持久化（缓存可重建部分除外）：

```text
CurrentGoal
CurrentStep
GoalStartedTick / StepStartedTick
AttemptCount
RecoveryLevel
LastResult
LastFailureReason
LastProgressSignature
TicksWithoutProgress
LastKnownPosition
LastTargetTile / Entity / Item
BossFailureCount
```

`ProgressSignature` 按任务定义，不只看坐标：

- 采集：目标资源数量增加、目标方块消失、距离缩短。
- 建造：缺失模板格数量减少。
- 合成：材料减少且产物增加。
- 导航：路径索引前进、到目标距离下降、进入新区域。
- 战斗：目标生命下降、阶段改变、躲避成功、目标死亡。
- 等待：等待条件确实变化；单纯经过时间不能永远算进展。

### 4.2 统一看门狗

为不同任务设合理窗口，禁止所有任务共用 60 tick：

- 近距离导航/拾取：约 3–5 秒无进展触发一级恢复。
- 采矿/砍树/放置：约 5–8 秒没有方块或库存变化触发。
- 长途区域导航：约 10–20 秒，期间必须有路径或区域进度。
- 条件等待：使用指数退避重新检查，同时执行不破坏条件的替代任务。
- Boss：一次死亡/脱战记为一次失败，不以几秒计时直接宣告卡住。

恢复层级冻结为：

1. 重新验证目标是否仍存在、站点是否被拆、配方是否仍可做。
2. 清除当前路径缓存并从实时位置重新寻路。
3. 选择同类的另一个目标（另一棵树、另一矿脉、另一落点、另一宝箱）。
4. 切换合法替代路线（宝箱没有跑鞋则钓鱼；材料不足则采购/挖掘；白天/天气不符则做库存和房屋任务）。
5. 回到已验证的 home/checkpoint，整理背包、补给和装备，再重建任务。
6. 对非 Boss 的纯导航死锁允许一次安全救援，但必须有严格条件：长时间无进展、目标合法、落点无危险、不能跨越未解锁地牢/神庙/世界硬门槛。不得把传送当日常寻路。
7. 所有替代路线也失败后进入有原因的 `Blocked*`，限频显示诊断并定期重试；不能静默原地抖动。

`RetryLater` 必须携带原因和下次检查时间。背包已满不得返回无限 `RetryLater`，必须生成 `DepositSurplus`；没有箱子则先生成“制作/放置箱子”子目标。`AlternativeRequired` 必须记录已经试过的目标，避免下一帧又选回同一个坏目标。

### 4.3 诊断

给自动伙伴增加仅在调试配置开启时显示的诊断：

- 世界阶段、能力阶段。
- 当前 Goal/Step。
- 目标坐标或实体。
- 成功判据与当前差值。
- 最近结果、无进展 tick、尝试次数、恢复层级。
- 阻塞原因、下次重试时间。
- 最近 8–16 条状态转换的环形日志。

日志必须限频，普通玩家默认看不到；不可每帧写磁盘或聊天。

### 4.4 立即应补的流程分支

完成看门狗后，按以下顺序补流程，不要直接跳 Boss：

1. **背包和仓库**：物品分类、保留清单、存箱、取回、箱子被拆后的恢复；保护任务关键物品。
2. **永久成长**：合法寻找并使用 Life Crystal、Mana Crystal、Life Fruit，实际递增现有独立计数字段。
3. **世界知识**：分帧扫描、缓存版本、世界修改失效、兴趣点优先队列；每帧有固定预算。
4. **宝箱与机动性**：开箱、装备评分、Hermes Boots 族、钩爪、瓶类跳跃；找不到时转钓鱼。
5. **NPC/购买**：房屋有效性、钱币统计、Merchant/其他 NPC 条件、Bug Net 与补给白名单。
6. **钓鱼替代**：鱼竿、鱼饵、水体大小、宝匣、停止条件和长期无收获的换池策略。
7. **主线提供器**：将 Eye 至 Moon Lord 分成世界里程碑与个人能力门槛；每个 Boss 独立策略，不用一个泛型追敌循环假装完成。

额外分支建议：

- 若世界已经由玩家推进，自动伙伴读取世界里程碑，但仍需补足自己的装备和生命；不能凭世界 flag 刷装备。
- 若召唤时世界已经击败 Moon Lord，不能未经说明立即把一名刚创建的铜工具伙伴标为“自己通关”。建议绑定创建时记录 `RunStartedAfterMoonLord`：这种世界进入“世界已完成，自动挑战无可执行主线”的明确状态，由书本提示后转换为普通伙伴，完成记录注明是继承世界完成，不计为自动流程成功。
- 建筑、站点、箱子被玩家拆除时，以实时世界为准重建，不信任旧坐标。
- 特殊种子没有提供器时进入 `BlockedUnsupportedWorld`，不继续盲挖。
- 模组 Boss/主线只通过明确 provider 接入；通用物品属性可以自然使用，但不得猜测模组进度。

### 4.5 自动书验收

- 人为在树前封一堵墙：重新寻路、换树或挖合法通路，不永久撞墙。
- 背包塞满：存箱/造箱，不无限 `RetryLater`。
- 拆除工作台、熔炉、铁砧、房屋墙、箱子：检测失效并恢复。
- 把目标矿挖掉、宝箱拿走、NPC 杀死：下一帧不继续操作陈旧目标。
- 让同一 Boss 连败三次：回到装备、药水、场地评估，完成一项真实提升后再挑战。
- 保存退出发生在采矿、建造、等待、Boss 准备和 Blocked 状态：重载后不复制物品、不丢 profile、不重置名字/背包，并能合理续跑或重建缓存。

## 5. 任务四：普通幻影伙伴的可选敌对阵营

### 5.1 配置与身份范围

新增一个玩法配置，建议名称：

```text
OrdinaryCompanionsHostileToPlayers = false
```

这是伤害规则，不能放在现有 ClientSide 配置中由每个客户端各自决定。新增 `MoreAIPlayerServerConfig`（`ConfigScope.ServerSide`），默认 `false`，同步九种本地化的 Label/Tooltip。

Tooltip 必须说明：

- 仅影响调试书召唤的普通幻影伙伴。
- 普通伙伴彼此同阵营，不会互相伤害。
- 它们仍只主动寻找敌对 NPC，不会把玩家选为 AI 目标。
- 玩家可以伤害它们；它们挥舞/发射的攻击若碰到玩家也会伤害玩家。
- 默认关闭，属于娱乐/测试功能。

身份不要仅靠“当前不是自动运行”判断。`AutoState.Running == false` 的通关自动伙伴仍保留自动历史，不应悄悄吃到本配置。建议给 profile 增加可迁移的 `CompanionOrigin`：

```text
OrdinaryDebug
Automation
```

旧存档中 `AutoState != null` 迁移为 `Automation`，其余普通 profile 迁移为 `OrdinaryDebug`。Hunter 不使用 `CompanionProfile` 的这条普通伙伴路径，因此天然排除，但仍要写显式断言/测试。

### 5.2 行为合同

开启后：

- 所有 `OrdinaryDebug` 伙伴属于同一个逻辑 AI 阵营。
- 它们之间、它们的 minion/sentry/子投射物之间不造成伤害。
- 运行中的自动伙伴、自动伙伴历史 profile、Hunter、镇民和普通 NPC 不因这个配置被改成同阵营或敌对。
- 普通伙伴仍然跟随、驻守、自由行动、挖矿、钓鱼和攻击敌对 NPC；`SelectTarget` 保持只返回 NPC，绝不增加 Player 目标分支。
- 不允许为了启用此功能强行修改真实玩家的 `team` 或 PvP 开关。
- 普通伙伴攻击玩家是“碰撞造成的误伤/敌对伤害”，不是主动瞄准、追击或报复。伙伴被玩家击中后也不能把玩家写进 `RequestedTarget`。

### 5.3 伤害实现方向

先检查本机 tModLoader 当前版本的 PvP hooks，优先复用原版命中、伤害、闪避、免疫帧和投射物命中语义。但合成 Player 在单人下可能被原版 PvP 条件排除，因此必须做实机验证；若原版 PvP 路径不触发，接入现有 `CompanionEntitySystem` 权威伤害通道，不得另写一套不带免疫帧的直接减血。

玩家 → 普通伙伴：

- 在配置开启时，即使 `CompanionsTakeDamage` 为 false，也允许“真实玩家来源”的伤害；该旧配置仍只决定 NPC、敌弹和环境是否伤害普通伙伴。
- 识别真实玩家近战 item hitbox、玩家及其 minion/sentry/子投射物。
- 排除伙伴自己、其他普通伙伴、Hunter、运行中的自动伙伴及无合法 owner 的投射物。
- 复用伙伴现有 `ownedDamageEvaluationTarget`、防御、闪避、格挡和 cooldown，保证一个挥击/弹幕不会每帧重复结算。

普通伙伴 → 玩家：

- 伙伴 item 攻击和其拥有的 projectile 与真实玩家碰撞时，在权威侧调用正常 `Player.Hurt` 语义。
- 必须保留伤害类型、方向、暴击/随机波动、玩家防御、闪避和免疫帧；不得直接 `statLife -= damage`。
- 伙伴仍瞄准 NPC。不要把玩家中心传给虚拟鼠标，不要修改 homing 目标为玩家。
- 第三方武器若内部自行搜索玩家或绕过通用 PvP，需要适配器；没有适配时宁可该武器不伤玩家，也不能违反“不主动攻击玩家”。

防双算：同一攻击若原版 PvP hook 已经结算，手动碰撞路由必须跳过。给攻击记录 `(sourceOwner, projectileIdentity/itemAnimation, targetPlayer, cooldownWindow)` 或使用原版免疫槽，避免一枚持续重叠弹幕重复命中。

### 5.4 阵营显示

可以给普通伙伴设置一致的视觉 team 颜色，但逻辑友军关系必须由本模组谓词决定，不能只依赖 `Player.team`。多人玩家可以选择任意原版队伍，固定 team 数字无法保证伙伴永远彼此友好且与所有玩家敌对。

建议集中函数：

```text
IsOrdinaryHostileCompanion(Player)
AreCompanionFactionAllies(Player a, Player b)
CanPlayerDamageCompanion(Player attacker, CompanionInstance target)
CanCompanionDamagePlayer(CompanionInstance attacker, Player target)
```

所有 item、projectile、minion、whip 和伤害 pass 共用这些判定。

### 5.5 配置验收

- 默认关闭：行为与当前版本逐项一致，不增加任何玩家/伙伴互伤。
- 开启后，玩家的近战、远程、魔法、召唤物可伤普通调试伙伴。
- 普通伙伴近战、枪弹、魔法弹、minion/sentry 在与玩家碰撞时可伤玩家，但其准星和移动仍指向 NPC/命令目标。
- 两名以上普通伙伴互相穿过弹幕不掉血。
- 自动伙伴、通关自动伙伴和 Hunter 不受该配置影响。
- 玩家攻击普通伙伴后，伙伴不追击玩家、不设置玩家目标、不改变自由行动/驻守锚点。
- 开关热更新后，旧弹幕的阵营处理有明确规则：建议以命中时配置和 owner 身份为准；关闭后立即不再产生新伤害。
- 与 `CompanionsTakeDamage` 的组合四种情况全部测试。
- 死亡、1/5/10 秒复活规则维持各自身份原有逻辑，不因玩家伤害来源改变。

## 8. 禁止的捷径

- 不要只把 `48f` 改大就声称平台修好了。
- 不要在战斗时完全禁止向下；正确目标是“只有经过批准才下降”。
- 不要把绳索当平台或用传送冒充攀爬。
- 不要在多人服务器占用真实连接玩家槽位。
- 不要仅因为当前公开声明单人就忽略专服、客户端加载和状态清理。
- 不要让 ClientSide 配置决定权威伤害。
- 不要把 `RetryLater` 当成可以无限重试的最终处理。
- 不要用传送、生成物品或改世界进度 flag 掩盖自动流程缺口。
- 不要让敌对普通伙伴主动选择玩家目标。
- 不要让普通伙伴互伤，也不要把 Hunter/自动伙伴混入普通调试伙伴阵营。
- 不要把“编译通过”写成“平台手感、多人同步、完整自动通关或 PvP 已实机验证”。

## 9. 最终完成定义

只有同时满足以下条件，本轮才可称为完成：

1. 平台下落由显式意图和安全落点控制，评论区场景实机不再无故掉落；绳索可进入、攀爬和退出。
2. 多人仍拒绝召唤，但客户端/专服安全加载与切换，自动审计没有发现无权限世界写入和槽位污染。
3. 自动书具备可观察、可持久化、分层恢复的看门狗，背包满、目标失效、路线失败、条件等待和 Boss 失败均有明确出口。
4. 自动书新增流程分支按本文优先级推进，未完成的阶段以诊断状态诚实暴露。
5. 敌对配置默认关闭；开启后只有普通调试伙伴与玩家可互相造成非主动瞄准式伤害，伙伴阵营内部完全友军。
6. 编译、HJSON、差异检查通过，并把所有未做的实机项目明确列出。
